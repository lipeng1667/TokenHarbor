## 已发现但未修复的旧代码问题

1. **缺失数据库配置时 Kernel 可能崩溃。** 第一次部署将配置误放在仅由 cwd 指定的位置；旧公共库实际按 `/proc/self/exe` 的目录找配置，导致 Kernel 使用空数据库参数并以 SIGSEGV 退出。源码显示 `dblog_new` 可返回 NULL，而 Kernel 未检查后访问 `hdb`。修正测试配置定位后不再发生；本轮未修改这一异常处理路径，也未进行 core/backtrace 分析。
2. **report 回执的 `resp_type` 字段存在异常。** 中间一轮实际观察到 `resp_code=2`、成功 result、正确订单号和 report TLV，但 `resp_type=0`。[保留证据](evidence/2026-11-05/earlier-report-branch.json)。Kernel `report_generate` 先设置 step=2，随后 `memcpy` 又覆盖它，Dispatcher 未显式设置对应字段。本轮确认 report 数据能够往返，**没有把该字段语义一致性计为通过项**，也没有修复它。
3. 配置、相对日志和订单持久化默认以可执行目录为基准；CDR 启动提示写 `.txt`，实际扩展名是 `.dat`。本轮用明确的配置/持久化链接和绝对日志路径完成部署，并按实际文件验证。

首次失败及中间检查失败的远端日志均保留，没有覆盖成成功结果。最终运行是修正构建/部署脚本后的独立新数据库验收。
