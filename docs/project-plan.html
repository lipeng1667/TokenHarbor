01 / CONTEXT

背景与项目定位

项目的核心资产，是可解释的调用与计费记录，以及持续可用的下游服务关系。

已经明确的起点 已知

  • 名称为 TokenHarbor，方向是统一接入文本、图片与视频 AI 能力，并按各能力的实际计量规则计费；不限于 Token。
  • GitHub 仓库已建立，本地项目从空目录开始。
  • 当前交付是 HTML 项目文档，尚未实现业务功能；客户通常调用平台 API，无须直接对接各供应商。
  • 计划在办公室和家中通过 GitHub 协作开发。

仍需验证的前提 待决策

  • 首批客户是谁，愿意为何种能力付费。
  • 能合法、稳定接入哪些供应商及账户。
  • 平台运营地区、数据处理地区和客户范围。
  • 团队能力、预算、币种、收款方式和预期负载。

潜在客户通常要分别处理供应商协议、API 差异、模型版本、用量统计和预算。TokenHarbor 的价值假设是：以统一身份与配额管理降低接入成本，以透明账单和可追溯日志降低运营成本，以受约束的多渠道路由改善可用性。是否比客户直接使用供应商更有价值，需要实际访谈和试点数据验证。

产品承诺的建议边界

提供已列明能力的统一接口、可核查的计费明细和清晰的失败状态。下游限制、授权范围和模型差异必须可见；不承诺“所有模型完全兼容”，也不将任何第三方账户视为天然具备转售资格。

本次讨论已对齐的边界

已确认方向 上游指客户（如广告公司、AI 应用团队），下游指运营商或模型厂商提供的 AI 能力接口。后文优先用“客户侧 / 供应商侧”避免歧义。调用链为客户 → Nginx → Portal → Kernel → Dispatcher → 下游。

用户倾向，未定案 借鉴 OES 的 Linux C + libevent 核心；不再把 C + Go 双语言设为默认方案。独立管理后台与业务核心分开，语言与通信协议待设计。

02 / BUSINESS

客户与商业假设

先选一个客群、一个主要场景和一种结算方式，验证闭环后再扩张。

候选客户需要验证的问题产品重点与代价
广告 / 内容制作公司批量图片与视频的吞吐、交付时限、素材权限、失败成本和回调接入要求？异步任务、结果查询、模型选择与可解释账单；作为讨论中的候选客群，尚非已签约客户。
独立开发者 / 小团队是否因多账户接入、充值管理或账单分散而困扰？是否接受预付费？易接入、API Key、明确余额；客服与小额交易成本可能偏高。
AI 应用与 SaaS 团队是否需要多渠道容灾、项目预算和稳定的错误契约？兼容性、限流、用量导出；对稳定性及账务解释要求更高。
企业内部平台是否允许数据经中间平台处理？采购及审计要求是什么？组织权限、数据地域、合同与合规；销售周期和交付复杂度更高。

模式 A：平台采购、按量销售

平台承担下游成本，以输入、输出及其他已明确计量项收取服务费。建议以预付余额试点；要核实转售授权、现金流、退款、税费和异常扣费争议。

模式 B：客户自带下游 Key

平台收订阅费或管理费，客户承担下游费用。减少采购敞口，但新增客户密钥托管责任；与平台余额模式应分开设计和计账。

起步建议 结合文本 API 与广告公司的图片 / 视频场景，访谈 3–5 个候选客户，记录现有月用量、最高并发、最常用模型、可接受中断和账单颗粒度。该数量是调研建议，不是已存在客户。

经营指标建议关注：有效接入率、首个成功调用时间、持续使用率、账单争议率、每活跃租户贡献毛利和支持工时。促销额度必须与付费余额分账，设置额度上限与到期规则。

03 / SCOPE

MVP 与范围边界

产品方向已确认 文本通常用 SSE；视频用异步任务与回调；图片默认异步，也可选择 SSE。具体模型、公开协议和首版交付顺序仍待确定，不表示这些能力已经上线。

目标闭环

  • 租户 / 用户、基础角色、API Key 创建与撤销。
  • 文本 SSE 与普通响应；图片 / 视频任务提交、状态查询、结果交付与回调。
  • 图片 SSE 明确区分任务事件与真实图片内容事件；开放能力以模型矩阵为准。
  • 一个供应商先跑通，再用第二个供应商验证适配边界。
  • 用量、价格版本、预占和结算、余额与调用明细。
  • 渠道配置、限流、熔断、审计、差异处理和恢复演练。

仍不默认纳入首版

  • 全模型 / 全协议兼容、自动跨模型语义替换。
  • 实时双向音视频、复杂图像工作流和自动素材编排。
  • 复杂代理商分销、返佣、信用赊账、多币种钱包。
  • 自动托管工具执行、浏览器代理或客户代码执行。
  • 微服务集群、多地域双活、复杂推荐与自动定价。
  • 未选定支付商前的真实充值、提现和金融功能。
验证额度与真实资金分开

早期在测试环境使用明确标注的模拟额度。正式收费前必须补齐支付订单、验证回调、重复回调去重、退款和对账规则；不能通过“直接改用户余额”代替资金流程。图片 / 视频可能按 Token、张数、时长、分辨率或任务计费，必须逐模型核实。

最低可用体验

用户创建 Key → 查询可用模型、交付模式与价格 → 发起请求 → 接收 SSE，或取得平台 task_id 后查询 / 等待回调 → 查看结果、用量来源、冻结 / 结算状态与余额变动。运营人员能沿 request_id / task_id 查到路由选择、供应商尝试、成本证据和账务凭证。

实施建议 用一条文本 SSE 和一条图片 / 视频异步任务验证两种生命周期，再扩展模型；是否同批交付、图片 SSE 的内容形式及取消能力由接口 ADR 决定。旧稿“视频与异步任务仅属未来扩展”的范围说明由本章取代。

04 / ARCHITECTURE

总体架构：Portal · Kernel · Dispatcher

已确认逻辑方向 借鉴 OES 的入口、调度和能力适配分层。实现未定案 用户倾向业务核心全 C + libevent；下面的持久化、账务与部署细节是建议设计，不是现有实现。

Nginx 与 libevent 各管哪一段

Nginx 有自己的事件处理框架，在 Linux 上可使用 epoll，并非基于 libevent。epoll 是 Linux I/O 就绪通知机制；libevent 在其上提供事件循环、定时器和缓冲 I/O 等封装，也支持其他后端。[10][11][12]

Nginx 终止客户入站 TLS，并不消除 Portal 的应用协议处理，也不替 Dispatcher 处理出站 HTTP/TLS、连接池、DNS、供应商认证与超时。

核心可全部由 C 实现

Portal、Kernel、Dispatcher、计费与恢复任务没有必须使用 Go 的理由；C 也能实现数据库事务和对账。关键是模块契约、资源所有权和可靠性，不是语言名称。事件循环中不可执行阻塞数据库 / DNS / 文件操作，应选非阻塞接口或有界工作线程 / 进程，方案待验证。

独立后台与关键业务状态

数据 / 动作建议边界
报表、历史调用、趋势展示独立后台服务可通过只读账号 / 视图或报表副本读 DB；允许约定的同步延迟，并展示数据更新时间。浏览器只访问后台 API，不直接连接数据库。
余额、冻结、额度放行、结算权威状态持久化，并由原子约束协调并发；不能依赖各 C 进程的延迟内存副本，也不能用有延迟的只读副本决定付费放行。
撤销 Key、禁用渠道、价格与策略生效写入经授权、校验与审计的版本化事务；定义生效时点和传播上限。WebSocket 可发变更通知，但断线后必须拉取版本 / 补偿，通知不是唯一事实来源。
核心故障与后台故障后台页面不可用应与已建立的流隔离；无法确认鉴权 / 预占成功时不发起新的付费请求。已开始请求仍可能产生成本，证据失败进入可恢复待对账流程。

内部契约：以 request_id / task_id / attempt_id、租户、请求指纹、价格和状态版本关联模块；预占、证据落库及结算定义幂等与超时语义。不把整条流放在数据库长事务中，也不让每条 SSE 长期占用数据库连接。

资源与配置：每条流有缓冲上限、读写超时与背压；下游证据不能只存进程内存。渠道与价格发布不可变版本，新请求用新版本，进行中请求继续用约定快照；安全撤销是否立即影响进行中任务要单独定义。缓存故障不能放开预算。

OES 的经验是起点，目标负载需要重测

已有短连接、高吞吐系统的调度与状态机经验可以复用；SSE 慢客户端、长时间异步任务、图片 / 视频结果交付需要不同的容量与恢复测试。全 C、全 Go、混合方案的对照见第 13 章；本文不承诺 C 必然更快。

05 / LIFECYCLE

SSE 与异步任务生命周期

客户侧交付方式与供应商侧调用方式是两套独立契约。内容 / 任务状态、账务状态、回调投递状态分别管理；已交付内容不代表最终用量已确认。

内容已确认的客户侧方向待设计边界
文本 / message通常选择 SSE，边生成边接收。保留普通响应；兼容端点、工具调用、usage 与流内错误契约待确定。
视频异步提交，取得 task_id；完成后平台回调客户。状态查询作为兜底；结果下载、取消、超时和留存策略需单独设计。
图片默认异步，也可选 SSE。SSE 可以承载真实阶段状态和最终结果；仅在供应商提供时发送逐图 / 部分图事件。不伪造百分比，不承诺所有模型都逐步出图。

共同调用与计费链 实现建议

  1. 客户 → Nginx → Portal：接收与校验

    生成 request_id；解析租户 Key、幂等键和请求指纹；检查请求体、模型权限、参数与交付模式、并发和速率。未通过校验不调用供应商。

  2. Portal → Kernel：规则与商业条件

    按用户 / 系统规则筛选能力、区域、渠道与价格快照。建议以短事务写请求、任务和预占；覆盖最大允许费用或受控追加，不能预扣固定小额却无限生成。确认持久化后才继续付费调用。

  3. Kernel → Dispatcher → 供应商：登记尝试并发送

    先持久化 attempt_id，再调用选定能力；保存供应商请求 / 任务 ID。发送与落库不可能成为同一个本地原子事务，崩溃窗口按执行未知处理，不能盲目重发。

  4. 结果返回：SSE 事件流，或持久化异步任务

    文本逐事件解析转发，记录首字节和首个内容时间。异步任务在平台已持久接收后返回 task_id，Dispatcher 依供应商协议查询或处理回调，再持久化任务状态和结果。

  5. Dispatcher → 核心持久化职责：用量证据

    保存必要原始 usage 与归一化结果、来源、版本和完成原因。缺失标为 provisional / unknown，不补零。无论用 C 或 Go，都不能只依赖内存中的一次通知。

  6. 计费职责：幂等结算与可靠事件

    建议同一短事务完成唯一凭证、余额变动、冻结释放、账务状态和 Outbox。异步恢复任务重复执行时，由唯一约束与条件迁移防双扣。

  7. 平台 → 客户：交付、查询与对账

    客户可查看任务和结算各自状态。回调投递独立重试；运营处理迟到用量与成本差异。更正使用追加调整凭证，不覆写账目。

文本 SSE：保持响应流

客户 POST → Portal / Kernel → Dispatcher 发起供应商请求 → 接收 SSE / 响应 → 平台按自己的契约向客户输出事件 → 持久化证据与结算。两侧连接独立管理；客户断线并不证明供应商已取消。

图片 / 视频：任务脱离连接存活

客户提交 → 平台持久化并返回 task_id → 后台继续执行 → 供应商回调或平台查询 → 保存最终状态与结果 → 平台回调客户。客户也能主动查询，关闭提交连接不会删除任务。

Dispatcher 不能只实现两种传输模式

供应商实际协议平台适配方式（建议）客户可见方式
同步响应 JSON / 结果链接持有下游请求直到结果；可由后台执行并保存。普通响应，或平台包装的异步任务；图片 SSE 可仅提供真实状态与最终结果。
SSE按供应商事件语义解析，不能把流分片直接当完整 JSON。规范化 SSE；也可后台消费后形成异步结果，需明确内容留存政策。
异步提交 + 状态查询映射供应商 task_id，调度有界轮询、退避与恢复。平台 task_id + 查询 / 平台回调；不要求供应商支持 webhook。
异步提交 + 供应商回调独立接收回调、验真和去重，再查询补漏（若支持）。平台自行投递客户回调；可附加任务事件 SSE，不等于视频内容逐帧流式生成。

SSE 的具体工程约束

环节建议设计
事件与 JSONtext/event-stream 是单向 HTTP 响应流；UTF-8、空行分隔事件，可有 event / data / id / retry。一段网络读取、一条 SSE 事件和一个业务 JSON 不是同一个边界；先处理跨块字符与事件，再交给 cJSON。[1]
代理与心跳对流式路由关闭不必要的响应缓冲（例如 Nginx proxy_buffering off），校准两侧空闲超时和 flush；心跳只说明连接存活。不能把发给客户的心跳当作供应商健康证据。[13]
客户端与断线恢复原生 EventSource 采用 GET，不能直接配置 POST 请求体或任意 Authorization 头；生成请求可用 fetch / SDK 读取流，或另设鉴权的任务事件订阅。event id / Last-Event-ID 不自动提供持久化重放；需要保存事件、游标、保留期与权限。未实现重放时只提供状态查询，不重新生成。[1]
头部与错误输出前可用 HTTP 错误；输出后不能改写状态码，按契约发送错误事件或结束流，并提供 request_id / task_id。错误码不得泄露供应商凭据。
背压与取消每流与全进程缓冲都有界；慢客户端触发暂停读取或终止策略。按已公开策略尝试取消供应商；取消不支持 / 结果未知时继续记录成本。libevent 缓冲封装不自动解决业务级总量上限。[12]
完成与日志分别记录内容完成、供应商终止、客户断线与账务完成；不能按 chunk 数 / 字数计费。普通日志只记边界事件和计量证据，不逐 Token 保存正文。
06 / ADAPTERS

供应商适配与模型版本

统一接口应发布一张可测试的能力矩阵。按供应商 × 端点 × 模型版本登记输入 / 输出、同步 / SSE / 异步、查询、回调、取消、计量与结果留存。工具调用、JSON Schema、缓存、推理及多模态均逐项验证，不把“兼容 OpenAI”理解为所有行为相同。

适配器职责

  • 将规范化请求映射为供应商协议。
  • 校验参数、格式、长度及工具能力；不支持时明确拒绝。
  • 解析流、错误、完成原因与用量维度。
  • 输出可重试判断所需的“已发送 / 已接受 / 未知”等证据。
  • 保留有限原始字段与来源，不把不同语义强行合并。

  • 公开模型名：客户端选择的稳定产品标识。

机制设计要点上线前验收
超时区分排队、连接、首字节、流空闲、客户端写入与总时长。所有重试共享总 deadline；按模型与场景配置。各类超时均有明确错误、账务去向和资源回收；无无限挂起。
重试与切换仅在确定未执行，或下游有已验证幂等保证时重试；遵守 Retry-After 与总预算。首个内容字节后不透明切换模型或供应商。模拟请求已送达但响应丢失，验证不会自动产生第二次生成。

限流租户 / Key / 模型 / 下游配额多层限制 RPM、TPM 与并发。预估 token 先预扣、实际用量再校正；排队有界。并发无配额穿透；拒绝返回明确可重试信息。已关闭连接可释放传输槽；供应商运行任务槽须确认终态 / 取消生效，未知任务保留风险预算，不因客户断线或轮询超时直接释放。
Redis 可选实现计数与过期必须原子化；官方 INCR 模式说明了分步更新的竞态风险。[6] 故障时对付费请求拒绝或采用经验证的保守上限。进程中断、TTL 异常、缓存重启不会放开预算。租户账务仍由数据库约束。

建议初始默认：执行结果不明时自动重试次数为 0；其余已确认安全场景最多 1 次重试。数值只是保守起点，需压测、成本数据与供应商协议验证后调整。

Kernel 与 Dispatcher 的分工：Kernel 先应用用户权限 / 预算 / 指定模型等规则，再应用系统的地区、渠道健康、权重和成本策略；Dispatcher 按选中的具体能力执行，不私自换成别的模型。供应商错误要映射为平台稳定分类，同时保留可追溯的原始错误引用。

异步限流分开计数：任务创建速率、运行中任务数、轮询频率、回调投递和结果下载分别设预算。供应商已接受后换渠道意味着另一笔真实生成，不能作为普通连接重试；本地轮询超时也不等于供应商任务失败。

08 / ACCOUNTING

计量与账务一致性

将用量事实、售卖价格、下游成本和资金变动分开保存，再以不可变版本关联。业务状态可以变化，已经发生的账务凭证只能追加修正。

四类记录，四种含义

Usage · 用量事实

原始维度、规范化分桶、模型 / 协议版本、证据来源（下游最终值 / 估计 / 账单核对）、证据时间。缺失值与 0 严格区分。

Price · 商业规则

币种、最小记账单位、计费维度、单价分子 / 分母、生效时间、舍入方式、用户价格方案和失败计费政策。

Cost · 平台采购成本

每个下游 attempt 单独记录成本与来源，包括失败重试。未知成本先作为估计或敞口，日后对账修正。

Ledger · 余额凭证

充值、扣费、退款和调整均关联唯一业务事件、操作者及理由。建议平衡分录或等价的可校验追加式账本，余额为同事务维护的可重建投影。

金额精度与版本

Token 数使用整数；金额使用固定最小单位的整数，单价可用定点数或整数比率；禁止二进制浮点累加金额。可采用 BIGINT 或有明确精度与溢出界限的 NUMERIC，接口把大整数序列化为十进制字符串。售卖价与采购价分别版本化，写入请求 / 尝试快照，不用当前价格重算历史账单。

计费金额 = Round价格版本 ( Σ [互斥计量桶数量 × 该桶单价] )
可用余额 A = 账面余额 B − 有效冻结 H
币种一致；每次结算只在已约定层级舍入一次；不能在每个 SSE chunk 上向上取整。

预占 → 结算 → 释放 → 对账 候选账务方案

  1. 预占：用输入估计、最大输出、允许的额外收费项计算保守上限 R。在事务内锁定钱包或用条件更新确保 B − H ≥ R，增加 H，并保存 reservation。无法界定成本上限的能力先不开放。
  2. 结算：获取可靠证据后计算实际费用 C。以请求为唯一初次结算对象，在同一事务中写凭证、更新 B = B − C、H = H − R、终结预占并创建 Outbox 事件。
  3. 释放：若可靠证据证明未调用 / 不应收费，则按同一状态条件释放 R。不能仅因锁过期、客户端断线或 Worker 超时就推断免费。
  4. 对账：按请求 / 下游标识、模型、时间和用量匹配供应商报告；若下游仅提供汇总账单，只能做聚合核对，将无法归因部分列为差异，不编造逐请求证据。

数据库事务只覆盖本地状态。建议对钱包行采取统一锁顺序，对关键迁移使用条件更新与唯一约束；若采用 Serializable，应用需处理序列化失败并重跑本地事务，不能因此重发下游生成请求。[5]

实际费用大于冻结金额怎么办？

这必须是受控异常，不是静默透支。优先通过参数上限与保守预占避免；发生时标记风险敞口，按已约定规则尝试追加预占。建议第一版不向未授权余额强行扣成负数；无法补足部分进入人工裁定 / 平台承担队列，并暂停相关计费配置排查。

金额算例 纯假设 · 非官方报价

假设结算单位为演示币 U，1 U = 1,000,000 μU；输入价 2 U / 百万 Token，输出价 8 U / 百万 Token。一次请求输入 1,200 Token、输出 300 Token、输出上限 1,000 Token；忽略缓存、工具、税费和汇率。采购价仅为演示，假设输入 1 U、输出 4 U / 百万 Token。

项目计算结果
请求前预占 R1,200 × 2 + 1,000 × 810,400 μU = 0.0104 U
实际售卖费用 C1,200 × 2 + 300 × 84,800 μU = 0.0048 U
释放剩余冻结10,400 − 4,8005,600 μU = 0.0056 U
采购成本1,200 × 1 + 300 × 42,400 μU = 0.0024 U
调用毛差额4,800 − 2,4002,400 μU；尚未扣运维 / 支付 / 争议成本

若初始 B = 1 U、H = 0，预占后 A = 0.9896 U；结算后 B = A = 0.9952 U、H = 0。总冻结 0.0104 U 在结算时解除，其中 0.0048 U 转为消费，剩余 0.0056 U 恢复可用。不是重复释放两次。

候选账务方案的关键约束

  • 同一请求最多一张初次消费凭证；调整凭证有独立幂等键并引用原凭证。
  • 单币种分录平衡，钱包投影与账本重建结果一致，正常业务下有效冻结与可用余额不为负。
  • 已终结预占不能重复释放或重新初次结算；迟到证据通过调整流程处理。
  • 账本、钱包投影、预占状态和 Outbox 在同一事务内提交；消息可重复投递，消费者必须幂等。
  • 先确保调用证据可恢复，再考虑异步报表速度；缓存和队列不是唯一事实来源。

全 C 计费与 T+1 对账并不冲突

讨论中的方案 C 核心可以负责计量、价格计算、额度控制与结算；数据库支持事务与唯一约束，对账按 T+1 日扫描匹配也可行。这里的关键区别是时效：报表可以延迟，对账可以次日，但付费调用前的额度竞争必须原子处理，执行后的证据必须可靠持久化。T+1 对账不能补救已经无限放行的费用敞口。

异步任务的提交成功不等于最终应收金额确定；按能力成本上限预占，任务完成后依据真实证据结算。生成失败、取消、超时和回调失败分别定义计费政策。平台重新发送完成通知，不再次调用模型，也不再次收取生成费用。

11 / TRUST

安全、隐私与下游授权

API Key 生命周期

  • 用安全随机源生成高熵密钥，创建时仅展示一次；数据库保存哈希与可识别前缀。
  • 限制项目、模型、预算、有效期；需要时支持 IP 范围。
  • 轮换提供短暂双 Key 过渡，撤销及时失效；缓存失效延迟纳入安全测试。
  • 管理端强认证、分角色授权；密钥和账务高风险操作审计。

租户与网络隔离

  • 租户身份来自已验证凭证，不信任客户端自报 tenant_id。
  • 请求、账单、导出和对象存储下载都检查资源归属。
  • 下游地址采用受控配置与出站白名单，禁止任意 URL 代理，防 SSRF。
  • 限制请求体、并发、输出长度和工具能力；试用额度设硬上限。

日志和数据最小化

业务日志默认只保存 request_id、租户标识、模型、状态、时延与计量结果；不保存 Authorization、下游密钥或完整提示词 / 回复。OWASP 对敏感数据排除与日志保护的建议可作为基线。[7] 如客户主动开启排障内容采样，应单独授权、加密、限时和审计，且可关闭。

数据类候选策略（待确认）必须验证
请求元数据 / 普通技术日志在线 30 天；聚合指标延长，精确时长依据成本与用途。自动删除、导出权限、索引与副本一致清理。
提示词 / 回复正文默认不留；经许可的排障样本最长 24 小时作为候选值。采样可关闭、密钥脱敏、访问审计、备份到期清理。
计费证据 / 账本 / 审计保留必要字段；期限由经营主体、合同和适用义务确定。更正可追溯；删除请求与法定 / 合同保留要求的处理流程。
备份加密、独立权限与明确轮换期限。恢复后重新执行删除 / 撤销策略，防止已删数据或 Key 回流。
授权与合规是上线门槛，当前尚未核实

逐个下游核实商业 API 使用权、是否允许代理 / 转售、账户共享限制、服务地区、数据处理和保留条款。确定运营主体、客户地区、部署地区后，再核实隐私、税务、支付和内容治理义务。本文不对任何供应商的授权或具体法律合规作出结论。

凭证放入部署环境的密钥管理设施，不写入 Git；生产与测试账户隔离。对滥用检测、投诉处理、暂停账户和费用争议制定流程。运营后台也遵循最小权限，人工调账应有理由、证据与复核。

任务、图片结果与回调的附加边界 建议

客户配置的 callback_url 与输入 / 输出素材 URL 都要防 SSRF：限制协议和端口、检查 DNS 解析结果与重定向、拒绝本地及内部保留地址，并限制连接时间与响应大小。平台发出的回调使用可验证签名；接收供应商回调按其真实协议验证，不能猜测签名规则。

task_id、事件游标和下载链接均校验租户归属。异步交付需要可用结果，但不意味着无限留存正文：单独定义结果 / 素材与 SSE 重放数据的客户授权、加密、有效期、删除及备份清理。未确定存储政策前不承诺跨设备内容续传。

12 / OPERATIONS

可观测性、成本与恢复

一条追踪链，两个经营视角

将 request_id / task_id → attempt_id → 供应商请求 / 任务 ID → usage 证据 → 凭证串联。追踪可采样，账务事实不可因采样丢失；避免把 request_id 作为高基数指标标签，详细定位放在日志 / 追踪中。

运行健康

平台拒绝与下游失败分开统计；记录首有效内容时延、总耗时、活跃流、队列等待、背压、熔断状态、数据库锁等待、结算积压与未知 usage 占比。

经营健康

收入、所有尝试的下游成本、未确认成本敞口、退款 / 拒付、支付费、促销消耗和基础设施费用分开。按租户、模型和渠道观察贡献毛利。

单次贡献 = 确认净收入 − 全部下游尝试成本 − 支付 / 退款成本 − 可归属基础设施成本
该式为运营分析口径，不替代财务收入确认。未知下游成本单列；重试成本与促销额度不可漏计。

售卖币种与采购币种不一致时，保存独立成本币种和固定的汇率快照；首版建议只开一种用户钱包币种。不要将充值额直接当成当期调用收入。

候选服务目标 压测后批准

  • 账务正确性：双扣、跨租户读取、无依据放开余额在验收中为零容忍。
  • 平台增量开销：定义“排除下游与主动排队的网关处理时间”，建议试点 P95 < 100 ms；必须在约定负载和环境下测量。
  • 用量完整度：正常完成且下游提供 usage 的请求，建议 99.9% 在 60 秒内完成结算；未知证据不混入成功样本。
  • 可用性：建议试点以月度 99.5% 为内部观察目标，同时报告端到端成功率与平台自身错误率；不是对外 SLA。

容量估算区分连接、请求流与任务

并发存活请求约等于到达率 × 平均存活时间。例如纯假设的 5 请求 / 秒、平均流长 20 秒，约有 100 条同时存活的流。这只是稳态估算，不是性能承诺。异步任务也可用到达率 × 任务持续时间估算在途量，但不等于需要同样多条客户连接。HTTP 复用下请求流与 TCP 连接也非一一对应。另计供应商连接池、轮询、客户订阅、回调及文件下载的资源；压测覆盖长尾、慢客户端、突发、租户偏斜和热钱包，不只报告 HTTP QPS。

部署数量与扩容路线 尚未部署

阶段数量与职责可用性边界
开发验证1 台：Portal / Kernel / Dispatcher、异步处理职责和 PostgreSQL 同机。适合验证，所有组件共用一个故障域，不具备 HA。
低成本试点2 台：一台业务模块与异步处理，一台数据库。应用与数据库仍各有单点；分开部署不等于高可用。
商业起步建议2 台业务 VM，跨可用区，每台部署业务模块与恢复 / 投递职责；另配高可用托管负载均衡及主备 PostgreSQL。“2 台”仅指业务机，托管服务及数据库主备资源另计。任意一台故障，另一台须能承受约定峰值；做 CPU / 内存资源隔离。
独立扩容阶段示例 4 台业务机：2 台接入 / Kernel，2 台 Dispatcher / 异步执行；也可继续同机多副本。按实测瓶颈拆分，数据层与入口资源另计。共享持久任务与账务状态；Kernel 和各关键能力 Dispatcher 都需可接替，不能因拆分制造单点。Worker 重复领取与结算须幂等。

Portal 扩容看活跃 SSE 流、文件描述符、内存和事件循环延迟；Kernel 看规则 / 预占延迟与共享状态竞争；Dispatcher 看供应商配额、活动请求、在途任务、轮询积压和出口带宽；恢复 / 投递职责看未结算量与回调积压。数据库先优化索引、短事务、连接池与热钱包锁竞争，再评估规格升级、报表读副本；余额判断与扣费不得依赖有延迟的读副本。新增服务器不会提高下游账户配额。扩缩容阈值、机器规格、区域、价格和容量基线需压测与预算审批后确定，不在此虚构报价。

高可用的验收条件

  • 负载均衡健康检查与自动摘除、多可用区故障隔离、N−1 容量均需测试。Redis 如成为必需共享限流依赖，须有 HA 或经验证的保守降级路径，不能成为新单点。
  • 发布先停止接收新请求，再等待连接排空并设置有界等待。节点宕机后，旧 SSE 流通常会中断，不能自动迁移续传；新请求可切至健康节点，不代表旧请求可安全重跑。
  • 数据库故障切换需检测、旧主隔离与单写者保障。核实托管方案的同步持久化和已确认账务 RPO；异步复制可能丢失最近事务，同步复制也有延迟与可用性取舍。[9]
  • 提交结果未知时先查询唯一凭证，再幂等重试本地事务；不得将数据库重试变成重新调用付费模型。缺失 usage、断流和不明结果进入差异单，不能直接当免费或立即解冻全部额度。
  • 模拟 Portal、Kernel、Dispatcher、恢复任务、数据库主节点、可用区与网络故障，检查请求状态、扣费、证据恢复和告警。只有实际通过约定的故障与恢复验收，才能宣称达到目标，不能凭两台机器承诺 SLA。

备份、迁移和事故恢复

建议 PostgreSQL 采用可恢复的备份方案与连续 WAL 归档 / PITR，并验证完整恢复链。官方文档说明了基础备份结合 WAL 回放的恢复机制。[8] Redis 可重建；凭证加密密钥需有独立、受控的恢复路径。

  1. 历史候选灾难恢复目标：RPO ≤ 15 分钟、RTO ≤ 2 小时；仅适用于待评审的备份恢复场景，不是在线故障切换目标，也不等于可以接受丢失已确认账务。两类目标须分别审批并通过演练量测。
  2. 事故期间暂停新的计费请求，保留请求与下游证据；切换前确保单一有效写入者，避免双主扣费。
  3. 恢复数据库后，对账本做余额重建与分录平衡检查；重放 Outbox 依靠幂等，不触发新的下游生成。
  4. 核对备份截止之后下游仍可能产生的费用、支付回调与撤销操作；未收敛差异先挂账。
  5. 数据库迁移先扩展兼容结构再切换，保留回滚预案；月度恢复演练及高风险升级前演练作为建议。
13 / TECH CHOICES

技术选型：全 C 倾向与对照验证

用户倾向，未最终定案 Portal / Kernel / Dispatcher 与计费核心优先研究 Linux C + libevent，借鉴 OES。v0.2 的“C 网关 + Go 账务”保留为备选，不再是当前主方案。独立后台可采用适合页面与管理的技术，不强制业务核心双语言。

C + Go
保留备选		仅在 C 数据路径的实测收益和业务层开发收益都明确时考虑。多语言构建、内部 RPC / IPC、故障链和部署复杂度；拆分不能规避账务关键路径，收益不足则不引入。

已有模块如何复用

用户已指出 OES 的 module-unstable 下有 cJSON，可作为 JSON 解析候选，避免重新造轮子。本次文档更新未重新审计该模块的具体版本与实现；复用前核实版本、许可证、补丁、内存所有权、线程使用方式、嵌套 / 大小限制，以及大整数精度和溢出边界。SSE 分帧、HTTP/TLS 与业务校验仍需独立实现和测试，不能把“已有 cJSON”理解为全部协议问题已解决。

libevent 把事件通知、定时器和缓冲 I/O 组织起来；一个 event_base 的循环由单线程执行，多线程 / 多进程拓展要明确连接归属和跨循环通信。Nginx 与核心的线程 / 进程数、连接池和 IPC 协议通过原型确定。[11][12]

对照原型的同一把尺子 尚未执行

用同硬件、同 Nginx/TLS 设置、同模拟供应商延迟与数据量、同业务约束比较：短请求吞吐、长 SSE 和慢客户、任务提交 / 查询 / 回调、失败恢复、热钱包并发；记录吞吐、P95 / P99 增量延迟、CPU、RSS、内存随时间增长和开发 / 排障成本。C 方案辅以 sanitizer、协议模糊测试与长时间资源检查；不先给出“性能碾压”的结论。

领域候选方案待验证
主存储PostgreSQL：权威账本、预占、任务与 Outbox。版本、锁竞争、连接池、主备持久化与恢复；内存和 Redis 不保存唯一余额。
缓存 / 异步Redis 按需；初期 DB Outbox + 可恢复执行职责，可由 C 实现。积压、轮询成本、重复投递与恢复；有证据再引入专用消息队列。
管理后台 / 前端独立后台读 DB，React / Vue / 服务端渲染待定。读写权限、敏感状态生效规则和审计，不让浏览器直连数据库。
部署初期容器化候选，不强制 Kubernetes；多副本与 HA 数据层见第 12 章。语言选择不等于可用性；区域、预算、规格与长连接上限待实测。

多设备开发约定

GitHub 作为源代码与文档的同步点。每台设备开始前检查工作区并拉取，使用分支隔离较大任务；切换设备前提交并推送清晰的小步改动。不要同步生产数据库、真实密钥或本地凭证。依赖版本、数据库迁移、样例配置和本地启动步骤应入库；真实环境变量各设备独立配置。

后续建议建立 ADR（架构决策记录）：记录问题、备选、选择、后果、验证方式与日期。首批 ADR 应覆盖 API 子集、后端语言、账务模型、流中断收费、未知用量处理和下游授权。

14 / DELIVERY

分阶段路线与验收条件

按证据进入下一阶段，不在需求未定时承诺日历工期。每阶段结束需记录验收结果与未决事项。

P0 · 决策与验证

先把边界写清楚

完成首批客群访谈、供应商授权核实、文本 / 图片 / 视频能力矩阵、币种及计费政策；比较语言方案和两侧协议。

退出条件：可签字确认的决策表；至少一个合法可用下游；断线 / 未知用量政策明确；测试预算和负责人明确。

P1 · 单供应商技术闭环

先做可恢复的一次调用

在测试额度环境验证一条文本 SSE 和一条图片 / 视频异步任务；完成鉴权、任务 ID 映射、查询 / 回调、usage、预占与结算。具体先后与模型待定。

退出条件：断线、超时、重复提交 / 回调、并发和崩溃注入后不双扣、不盲目再生成；余额可重建；未决记录可扫描恢复。

P2 · 多供应商与试点

验证抽象是否成立

第二个供应商、不同下游协议组合、图片可选 SSE、明确路由、限流熔断、用户账单与对账台。

退出条件：适配器契约测试通过；无透明危险重试；固定负载下达到批准的性能目标；恢复演练通过。

P3 · 正式收费准备

让资金和运营可闭环

支付商验证、充值 / 退款 / 拒付、权限、告警、客服与隐私流程。

退出条件：支付回调去重与金额核对通过；合规 / 合同核实完成；账单能对到采购成本；事故与争议有人处理。

P4 · 依据证据扩展：企业组织能力、更多协议与模型、多地区部署。音频与实时交互等新增方向仍需独立评审；文本 / 图片 / 视频已经进入产品方向，开放哪些模型与功能由前述验收决定，不能硬套文本 Token 账单。

开发时必须覆盖的验收矩阵

类别可执行验证通过标准
计费单元与性质测试大整数、边界 Token 数、价格版本、舍入、缓存子集、缺失字段。同一证据可重复计算；金额无漂移、无重复包含。
并发与幂等预算只够一次时并发发起多请求；同幂等键重复；结算重复投递。不会超额放行；一个逻辑请求最多一张初次消费凭证。
流协议UTF-8 字符跨分片、多行事件、usage 空值、流内错误、未知事件、慢客户端。内容和终止状态正确；有界内存；无遗漏的结算记录。
故障注入预占后崩溃、下游已接受时断网、usage 后崩溃、提交结果丢失、恢复重放。不盲目重发；每个请求最终收敛至结算 / 释放 / 有负责人差异单。
异步协议与通知创建响应丢失、重复 / 迟到 / 乱序回调、查询超时、回调重放、租约接替与结果链接到期。生成 / 账务 / 投递三态可解释；不重复生成；通知重试不重复收费；无权租户无法查询 / 下载。
安全与隔离跨租户枚举、撤销 Key、日志扫描、恶意下游地址、大请求、权限提升。跨租户访问被拒；密钥不进入日志；地址与资源限制有效。
运维与真实对账备份恢复、真实小额下游样本对账、统计与账本重建、目标负载长连接压测。恢复目标实测达标；差异可解释；采购账单与内部证据可对应。

开发前优先回答的 8 个问题

D01

首批服务谁，为何愿意付费？

决定首个使用场景与验收指标；建议先访谈开发团队。负责人：产品，时间：P0。

D02

哪些下游账户可用于此商业模式？

列供应商、合同依据、区域与配额；无授权证据不上生产。负责人：经营，时间：P0。

D03

首版协议和功能子集是什么？

方向已确认：文本通常 SSE、视频异步、图片默认异步可选 SSE；确定具体端点、首版模型、查询 / 回调与事件契约，及工具调用、缓存和推理维度。负责人：产品 + 后端，时间：P0。

D04

未知用量、流中断和取消怎样收费？

选择证据优先级、冻结期限、估计是否可入账、后补扣费与平台承担条件。负责人：产品 + 经营，时间：P0。

D05

币种、余额、价格与退款政策怎样定义？

确认记账精度、舍入、价格生效、预付模式与支付渠道。真实收费前完成；原型只用测试额度。

D06

选择什么技术栈和部署区域？

当前倾向全 C + libevent，尚未定案；用全 Go 和混合方案作对照，依据团队经验、供应商地域、预算及 SSE / 异步任务 / 故障测试确定。负责人：技术，时间：P0–P1。

D07

需要多大容量、保留什么数据？

确定并发、平均 / 长尾流长、日志与证据留存、客户数据限制、RPO / RTO。负责人：技术 + 产品，时间：P1 前。

D08

谁处理故障、差异与客户争议？

指定值守、调账复核、告警升级和上线签字角色；即使团队很小也需明确责任。时间：试点前。

下一步建议

先完成 D01–D04 和一个小型技术验证：一条真实授权的文本 SSE 与一条图片 / 视频异步任务，在正常结束、断流、重复提交、回调重放和进程重启时，都能得到可解释的调用、交付与账务结果。再根据验证结果确认最终技术栈与开发计划。

16 / REFERENCES

术语与官方来源

核心术语

上游 / 下游：本项目上游为客户，下游为 AI 能力提供方；外部文档可能采用另一视角。
Token：模型处理的计量单位，不等同于字数。
SSE：HTTP 事件流格式，用于逐步传输结果。
Task：可脱离客户连接持续执行的持久任务，独立于一次 HTTP 请求。
Tenant：拥有独立权限、预算和数据边界的客户主体。
Attempt：逻辑请求中的一次实际下游尝试。
Reservation：预占 / 冻结额度，不是最终消费。

工程术语

Outbox：在业务事务内记录待处理事件，再由后台可靠投递。
Idempotency：重复处理同一业务动作不重复产生副作用。
PITR：恢复到指定时间点。
RPO / RTO：可接受数据损失窗口 / 恢复服务时长。
ADR：记录架构选择及理由的决策文档。
