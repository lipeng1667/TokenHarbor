01 / CONTEXT

背景与项目定位

项目的核心资产，是可解释的调用与计费记录，以及持续可用的上游服务关系。

已经明确的起点 已知

  • 名称为 TokenHarbor，方向是多家大模型统一 API 与按 Token 计费。
  • GitHub 仓库已建立，本地项目从空目录开始。
  • 当前任务是形成 HTML 项目文档，尚未实现业务功能。
  • 计划在办公室和家中通过 GitHub 协作开发。

仍需验证的前提 待决策

  • 首批客户是谁，愿意为何种能力付费。
  • 能合法、稳定接入哪些供应商及账户。
  • 平台运营地区、数据处理地区和客户范围。
  • 团队能力、预算、币种、收款方式和预期负载。

潜在客户通常要分别处理供应商协议、API 差异、模型版本、用量统计和预算。TokenHarbor 的价值假设是：以统一身份与配额管理降低接入成本，以透明账单和可追溯日志降低运营成本，以受约束的多渠道路由改善可用性。是否比客户直接使用供应商更有价值，需要实际访谈和试点数据验证。

产品承诺的建议边界

提供已列明能力的统一接口、可核查的计费明细和清晰的失败状态。上游限制、授权范围和模型差异必须可见；不承诺“所有模型完全兼容”，也不将任何第三方账户视为天然具备转售资格。

02 / BUSINESS

客户与商业假设

先选一个客群、一个主要场景和一种结算方式，验证闭环后再扩张。

候选客户需要验证的问题产品重点与代价
独立开发者 / 小团队是否因多账户接入、充值管理或账单分散而困扰？是否接受预付费？易接入、API Key、明确余额；客服与小额交易成本可能偏高。
AI 应用与 SaaS 团队是否需要多渠道容灾、项目预算和稳定的错误契约？兼容性、限流、用量导出；对稳定性及账务解释要求更高。
企业内部平台是否允许数据经中间平台处理？采购及审计要求是什么？组织权限、数据地域、合同与合规；销售周期和交付复杂度更高。

模式 A：平台采购、按量销售

平台承担上游成本，以输入、输出及其他已明确计量项收取服务费。建议以预付余额试点；要核实转售授权、现金流、退款、税费和异常扣费争议。

模式 B：客户自带上游 Key

平台收订阅费或管理费，客户承担上游费用。减少采购敞口，但新增客户密钥托管责任；与平台余额模式应分开设计和计账。

起步建议 优先验证小型开发团队的文本 API 场景，访谈 3–5 个候选客户，记录现有月用量、最高并发、最常用模型、可接受中断和账单颗粒度。该数量是调研建议，不是已存在客户。

经营指标建议关注：有效接入率、首个成功调用时间、持续使用率、账单争议率、每活跃租户贡献毛利和支持工时。促销额度必须与付费余额分账，设置额度上限与到期规则。

03 / SCOPE

MVP 与范围边界

第一版闭环 建议

  • 租户 / 用户、基础角色、API Key 创建与撤销。
  • 一个明确的文本 API 子集，支持普通响应与 SSE。
  • 一个供应商先跑通，再用第二个供应商验证适配边界。
  • 输入 / 输出用量、价格版本、预占和结算、余额查询。
  • 调用明细、可解释错误、成本统计、人工差异处理。
  • 渠道配置、限流、熔断、审计和恢复演练。

暂不进入第一版

  • 全模型 / 全协议兼容、自动跨模型语义替换。
  • 实时音视频、视频生成、图像工作流、异步长任务。
  • 复杂代理商分销、返佣、信用赊账、多币种钱包。
  • 自动托管工具执行、浏览器代理或客户代码执行。
  • 微服务集群、多地域双活、复杂推荐与自动定价。
  • 未选定支付商前的真实充值、提现和金融功能。
验证额度与真实资金分开

早期在测试环境使用明确标注的模拟额度。正式收费前必须补齐支付订单、验证回调、重复回调去重、退款和对账规则；不能通过“直接改用户余额”代替资金流程。视频只作为未来计量维度扩展。

最低可用体验

用户创建 Key → 查询可用模型与价格 → 发起一次请求 → 获得内容或明确错误 → 查看 request_id、用量来源、冻结 / 结算状态与余额变动。运营人员能从同一个 request_id 查到路由选择、上游尝试、成本证据和账务凭证。

04 / ARCHITECTURE

总体架构

2026-11-04 讨论稿：将调用转发核心与业务账务核心分开。建议 C + libevent 承担网关，Go 承担业务、账务与 Worker，PostgreSQL 作为权威账本；这不是已批准或已实现的技术选型。

先划清职责，再验证语言选择

借鉴 OES 的 Linux C、事件驱动、连接管理与显式状态机思想，不照搬其业务协议。C 并非高并发的必选项；应以同一负载的 C + Go 与纯 Go 原型对照，验证收益是否抵消内存安全、协议解析和双语言维护成本。

转发核心的边界

C 负责协议与长连接，不嵌入复杂价格规则或独立余额账本。每条流有缓冲上限、读写超时与背压；阻塞操作不得卡住事件循环。Go 调用失败且无法确认预占成功时，不发起新的付费上游请求。

Go 不只是管理后台

鉴权和额度预占处于每次收费请求的关键路径，同样需要多实例与可观测性。初期一个 Go 项目内划分用户、渠道、账务、后台任务等模块，不急于拆成大量微服务或跨服务资金事务。

内部契约：用 request_id / attempt_id、请求指纹、价格版本和状态版本关联 C 与 Go；预占、证据落库及结算接口均定义幂等与超时语义。内部通信协议和鉴权方案需原型验证后确定。整个流不占用一条数据库事务或连接。

故障边界：数据库不可用时拒绝新的付费请求；已开始请求仍可能产生成本，证据写入失败需进入可恢复的待对账流程。不能只把 usage 放在 C 进程内存并假定最终会送达。缓存故障不能放开预算；管理界面故障应与已建立的流隔离。

配置一致性：渠道与价格发布为不可变版本，记录操作者和原因。新请求使用新版本，进行中的请求继续使用快照。数据库保存权威余额，缓存仅作加速；不能在多台网关分别按本地余额放行。

05 / LIFECYCLE

请求与 SSE 生命周期

内容交付状态与账务状态是两条独立轴：用户已收到内容，不一定表示最终用量已经可确认。

  1. 接收 · 客户端 → 网关

    生成 request_id；解析租户 Key、幂等键和请求指纹；检查请求体大小、模型权限、支持参数、并发与速率。未通过校验不调用上游。

  2. 锁定商业条件 · C 网关 → Go → PostgreSQL

    快照模型映射、路由与售卖价格版本；确定允许的上游候选及输出上限；用短事务写请求、冻结余额和预占记录。预占失败即拒绝。预占须覆盖允许的最大费用，或采用受控追加机制；不能固定预扣小额却允许无限生成。

  3. 登记尝试后发出 · 网关 → 供应商

    先持久化 attempt_id 与待发送状态，再调用上游。发送与数据库更新不能成为一个原子事务；崩溃窗口必须按“执行结果未知”处理。

  4. 读取响应 / 逐事件转发 · 供应商 → 网关 → 客户端

    记录上游 request_id、首字节与首个有效内容时间。完整解析 UTF-8 和 SSE 事件边界；一条网络分片不等于一条事件。普通响应在完整校验后返回；流式响应按协议逐步转发。

  5. 归一化证据 · C 网关 → Go → PostgreSQL

    保存原始 usage 的必要字段与归一化结果、来源、版本、完成原因。最终 usage 缺失时，标为 provisional / unknown，不把“未获得”写成零。

  6. 结算 · Go 短事务 / 可恢复 Worker

    同一事务完成唯一结算凭证、余额变动、冻结释放和账务状态变更，并写 Outbox。任务重复执行时由唯一约束与条件迁移防止重复扣费。

  7. 展示与补偿 · 控制台 / 对账任务

    用户看到交付状态和结算状态；运营对超时未决、迟到 usage、成本差异进行核对。修正使用追加调整凭证，不覆写已发生账目。

流式传输的具体约束

环节建议设计
协议与代理使用 text/event-stream；关闭不必要的代理缓冲，验证负载均衡器空闲超时；事件按 UTF-8 与空行边界解析。浏览器原生 EventSource 的重连行为不等于生成请求幂等，需按具体客户端实现控制。[1]
头部与错误开始输出前可返回标准 HTTP 错误；输出后无法改写已经发送的状态码。根据公开接口契约发送错误事件或终止流，并提供 request_id 查询状态。禁止向客户端暴露上游凭证。
背压与断线为慢客户端设置有界缓冲和写入超时；断开后尝试取消上游，不能据此假定取消成功或成本为零。终止后进入独立、有时间上限的结算 / 对账流程。
完成信号分别记录内容完成、上游终止、客户端断线和账务完成。即使已有协议终止标记，账务也应由实际 usage 证据决定；不能从 chunk 数或字数直接计费。
日志不要将每个 token 或正文写进普通日志；只记录边界事件、时延和计量证据。单次流不应无限增长内存。
06 / ADAPTERS

供应商适配与模型版本

统一接口应发布一张可测试的能力矩阵。建议从文本对话、输入 / 输出上限、普通响应和 SSE 开始；工具调用、JSON Schema、缓存、推理、视觉和多模态必须逐项验证后开放。

适配器职责

  • 将规范化请求映射为供应商协议。
  • 校验参数、格式、长度及工具能力；不支持时明确拒绝。
  • 解析流、错误、完成原因与用量维度。
  • 输出可重试判断所需的“已发送 / 已接受 / 未知”等证据。
  • 保留有限原始字段与来源，不把不同语义强行合并。

模型标识分三层

  • 公开模型名：客户端选择的稳定产品标识。
  • 内部映射版本：绑定能力、价格和允许路由。
  • 上游真实模型版本：实际请求与响应中的标识，连同供应商和区域保存。

别名升级需灰度与回滚；不要悄悄切到能力不同或价格不同的模型。跨供应商替代须事先约定并显式披露。

官方行为示例对 TokenHarbor 的设计影响验证方式
OpenAI Chat Completions 的流式 usage 可在最后一个 usage chunk 提供；中断时可能收不到。[2]适配器显式请求支持的 usage；缺失进入待核对。该行为不自动适用于 Responses 或其他 API。完整结束、输出中断、终止前断线；不能默认最终 usage 必达。
Anthropic Messages 的 message_delta usage 为累计值；流中可能包含错误与新事件类型。[3]按字段语义合并累计值，不能逐事件求和；保留已知状态并安全处理未知事件。重复 / 多次累计更新、错误事件、未知事件、部分工具参数。
Gemini 提供调用前 token 计数及调用后 usage 维度。[4]前置计数用于预算，不替代最终结算；不同端点的字段名需独立映射。输入计数与实际 usage 的差异；缓存 / thinking 等字段的含义与包含关系。
禁止重复计算用量

缓存输入、推理输出可能是某个总量的子集，而不是额外加项。每个供应商 / 端点 / 模型版本都应定义字段包含关系，形成互斥的计费分桶；未知维度先停用相关能力或挂账，不按猜测收费。

供应商准入还需记录：协议版本、数据区域、超时 / 取消语义、幂等支持范围、凭证配额、用量查询与账单能力。只有经测试和授权核实的渠道才能进入生产候选池。

07 / RESILIENCE

路由、超时、熔断与限流

先过滤资格

租户策略 → 区域与授权 → 模型与能力 → 健康状态 → 配额与预算。不能为了低价越过地域或能力限制。

再选择渠道

初版采用显式优先级与权重；后续再依据时延、成功率和成本调整。记录候选快照、选择原因和实际成本版本。

最后决定是否重试

从“是否可能已执行”判断，而非仅看 HTTP 码。SDK 内置重试也必须计入平台统一重试预算。

机制设计要点上线前验收
超时区分排队、连接、首字节、流空闲、客户端写入与总时长。所有重试共享总 deadline；按模型与场景配置。各类超时均有明确错误、账务去向和资源回收；无无限挂起。
重试与切换仅在确定未执行，或上游有已验证幂等保证时重试；遵守 Retry-After 与总预算。首个内容字节后不透明切换模型或供应商。模拟请求已送达但响应丢失，验证不会自动产生第二次生成。
熔断按供应商账户 / 端点 / 模型隔离，滑动窗口加最小样本，半开限量探测。单租户输入错误不应熔断全渠道。故障渠道被隔离、恢复后渐进放量；探测调用计入成本。
限流租户 / Key / 模型 / 上游配额多层限制 RPM、TPM 与并发。预估 token 先预扣、实际用量再校正；排队有界。并发无配额穿透；拒绝返回明确可重试信息；取消 / 超时释放并发槽。
Redis 可选实现计数与过期必须原子化；官方 INCR 模式说明了分步更新的竞态风险。[6] 故障时对付费请求拒绝或采用经验证的保守上限。进程中断、TTL 异常、缓存重启不会放开预算。租户账务仍由数据库约束。

建议初始默认：执行结果不明时自动重试次数为 0；其余已确认安全场景最多 1 次重试。数值只是保守起点，需压测、成本数据与供应商协议验证后调整。

08 / ACCOUNTING

计量与账务一致性

将用量事实、售卖价格、上游成本和资金变动分开保存，再以不可变版本关联。业务状态可以变化，已经发生的账务凭证只能追加修正。

四类记录，四种含义

Usage · 用量事实

原始维度、规范化分桶、模型 / 协议版本、证据来源（上游最终值 / 估计 / 账单核对）、证据时间。缺失值与 0 严格区分。

Price · 商业规则

币种、最小记账单位、计费维度、单价分子 / 分母、生效时间、舍入方式、用户价格方案和失败计费政策。

Cost · 平台采购成本

每个上游 attempt 单独记录成本与来源，包括失败重试。未知成本先作为估计或敞口，日后对账修正。

Ledger · 余额凭证

充值、扣费、退款和调整均关联唯一业务事件、操作者及理由。建议平衡分录或等价的可校验追加式账本，余额为同事务维护的可重建投影。

金额精度与版本

Token 数使用整数；金额使用固定最小单位的整数，单价可用定点数或整数比率；禁止二进制浮点累加金额。可采用 BIGINT 或有明确精度与溢出界限的 NUMERIC，接口把大整数序列化为十进制字符串。售卖价与采购价分别版本化，写入请求 / 尝试快照，不用当前价格重算历史账单。

计费金额 = Round价格版本 ( Σ [互斥计量桶数量 × 该桶单价] )
可用余额 A = 账面余额 B − 有效冻结 H
币种一致；每次结算只在已约定层级舍入一次；不能在每个 SSE chunk 上向上取整。

预占 → 结算 → 释放 → 对账

  1. 预占：用输入估计、最大输出、允许的额外收费项计算保守上限 R。在事务内锁定钱包或用条件更新确保 B − H ≥ R，增加 H，并保存 reservation。无法界定成本上限的能力先不开放。
  2. 结算：获取可靠证据后计算实际费用 C。以请求为唯一初次结算对象，在同一事务中写凭证、更新 B = B − C、H = H − R、终结预占并创建 Outbox 事件。
  3. 释放：若可靠证据证明未调用 / 不应收费，则按同一状态条件释放 R。不能仅因锁过期、客户端断线或 Worker 超时就推断免费。
  4. 对账：按请求 / 上游标识、模型、时间和用量匹配供应商报告；若上游仅提供汇总账单，只能做聚合核对，将无法归因部分列为差异，不编造逐请求证据。

数据库事务只覆盖本地状态。建议对钱包行采取统一锁顺序，对关键迁移使用条件更新与唯一约束；若采用 Serializable，应用需处理序列化失败并重跑本地事务，不能因此重发上游生成请求。[5]

实际费用大于冻结金额怎么办？

这必须是受控异常，不是静默透支。优先通过参数上限与保守预占避免；发生时标记风险敞口，按已约定规则尝试追加预占。建议第一版不向未授权余额强行扣成负数；无法补足部分进入人工裁定 / 平台承担队列，并暂停相关计费配置排查。

金额算例 纯假设 · 非官方报价

假设结算单位为演示币 U，1 U = 1,000,000 μU；输入价 2 U / 百万 Token，输出价 8 U / 百万 Token。一次请求输入 1,200 Token、输出 300 Token、输出上限 1,000 Token；忽略缓存、工具、税费和汇率。采购价仅为演示，假设输入 1 U、输出 4 U / 百万 Token。

项目计算结果
请求前预占 R1,200 × 2 + 1,000 × 810,400 μU = 0.0104 U
实际售卖费用 C1,200 × 2 + 300 × 84,800 μU = 0.0048 U
释放剩余冻结10,400 − 4,8005,600 μU = 0.0056 U
采购成本1,200 × 1 + 300 × 42,400 μU = 0.0024 U
调用毛差额4,800 − 2,4002,400 μU；尚未扣运维 / 支付 / 争议成本

若初始 B = 1 U、H = 0，预占后 A = 0.9896 U；结算后 B = A = 0.9952 U、H = 0。总冻结 0.0104 U 在结算时解除，其中 0.0048 U 转为消费，剩余 0.0056 U 恢复可用。不是重复释放两次。

不可破坏的约束

  • 同一请求最多一张初次消费凭证；调整凭证有独立幂等键并引用原凭证。
  • 单币种分录平衡，钱包投影与账本重建结果一致，正常业务下有效冻结与可用余额不为负。
  • 已终结预占不能重复释放或重新初次结算；迟到证据通过调整流程处理。
  • 账本、钱包投影、预占状态和 Outbox 在同一事务内提交；消息可重复投递，消费者必须幂等。
  • 先确保调用证据可恢复，再考虑异步报表速度；缓存和队列不是唯一事实来源。
09 / FAILURE MODES

幂等、未知结果与异常收敛

系统只能通过数据库约束实现本地结算不重复；不能无条件保证跨网络生成“恰好一次”。因此应分别管理逻辑请求、每次上游尝试和每次账务事件。

RECEIVED→RESERVED→DISPATCHING→STREAMING / WAITING→COMPLETED / FAILED / UNKNOWN
HELD→AWAITING_USAGE→SETTLED / RELEASED+ADJUSTMENT（独立凭证）

平台幂等契约建议

对约定的生成接口使用租户 + 端点 + Idempotency-Key 唯一键，并保存规范化请求的指纹。同键同请求：返回已有状态或明确的进行中提示；同键不同请求：返回冲突。与模型相关的全部有效参数及价格快照都需关联。建议保留窗口至少覆盖客户端重试和最长对账处理窗口，实际时长待决策。

流式响应如果没有安全保存完整内容，就不能声称能重放历史流。建议 MVP 重复请求返回状态 / 凭证查询指引，明确不重新生成；幂等结果查询也必须按租户鉴权。普通响应是否短期保留用于重放，须与隐私策略一起确定。

窄屏可横向滚动查看异常处理矩阵。

事件 / 证据调用处理账务处理与恢复
鉴权失败 / 预算不足拒绝，不发上游请求。无消费；若已预占但未发送，按原子条件释放。
明确在发送前连接失败可在总 deadline 和同一预占内选择合格渠道；必须有未发送的证据。记录失败 attempt；不因连接失败自动创建消费。
上游可能已执行，响应丢失标记 UNKNOWN，不默认重试或跨渠道切换；若存在已验证查询 / 幂等机制，再按协议恢复。保持待核对，记录成本敞口；核对上游记录。不得把未知当作零用量。
客户端在流中断开尝试取消并记录取消结果；后续恢复工作有独立 deadline。按最终证据与事先公开的中断计费政策结算。取消请求不等于上游停止计费。
流正常结束但 usage 缺失保留交付完成状态；对账任务继续。不展示为已确认费用；估计只能标为预估。超出处理时限进入人工裁定，不无限冻结。
迟到 usage / 更正 usage按证据来源、序号或内容哈希去重。未结算时完成结算；已结算时计算差额并追加调整。已释放后不得再消费同一 reservation；追加收费需符合用户约定及额度政策。
并发重试 / Worker 重复投递唯一幂等键认领同一请求；每个实际 attempt 独立编号。唯一凭证 + 状态条件防双扣；消费者确认消息前提交事务。
进程崩溃 / 结算提交结果未知租约与扫描器识别失联任务。调用是否已发送不清楚时不重新生成。先查询唯一凭证是否存在，再幂等重试本地结算；不可凭内存结果直接再扣。
冻结超时 / 长期无上游证据超过业务处理期限后升级人工处理。冻结到期只触发核对任务。按公开政策在限定时间内选择释放、确认收费或平台承担，留下决定与通知记录。
对账队列必须有人负责

为每条异常设负责人、处理期限、金额上限和升级路径。建议待定 usage 超过 30 分钟告警，24 小时进入人工处置；这些是试点候选值，必须与上游报表延迟、客户条款和实际能力匹配。

11 / TRUST

安全、隐私与上游授权

API Key 生命周期

  • 用安全随机源生成高熵密钥，创建时仅展示一次；数据库保存哈希与可识别前缀。
  • 限制项目、模型、预算、有效期；需要时支持 IP 范围。
  • 轮换提供短暂双 Key 过渡，撤销及时失效；缓存失效延迟纳入安全测试。
  • 管理端强认证、分角色授权；密钥和账务高风险操作审计。

租户与网络隔离

  • 租户身份来自已验证凭证，不信任客户端自报 tenant_id。
  • 请求、账单、导出和对象存储下载都检查资源归属。
  • 上游地址采用受控配置与出站白名单，禁止任意 URL 代理，防 SSRF。
  • 限制请求体、并发、输出长度和工具能力；试用额度设硬上限。

日志和数据最小化

业务日志默认只保存 request_id、租户标识、模型、状态、时延与计量结果；不保存 Authorization、上游密钥或完整提示词 / 回复。OWASP 对敏感数据排除与日志保护的建议可作为基线。[7] 如客户主动开启排障内容采样，应单独授权、加密、限时和审计，且可关闭。

数据类候选策略（待确认）必须验证
请求元数据 / 普通技术日志在线 30 天；聚合指标延长，精确时长依据成本与用途。自动删除、导出权限、索引与副本一致清理。
提示词 / 回复正文默认不留；经许可的排障样本最长 24 小时作为候选值。采样可关闭、密钥脱敏、访问审计、备份到期清理。
计费证据 / 账本 / 审计保留必要字段；期限由经营主体、合同和适用义务确定。更正可追溯；删除请求与法定 / 合同保留要求的处理流程。
备份加密、独立权限与明确轮换期限。恢复后重新执行删除 / 撤销策略，防止已删数据或 Key 回流。
授权与合规是上线门槛，当前尚未核实

逐个上游核实商业 API 使用权、是否允许代理 / 转售、账户共享限制、服务地区、数据处理和保留条款。确定运营主体、客户地区、部署地区后，再核实隐私、税务、支付和内容治理义务。本文不对任何供应商的授权或具体法律合规作出结论。

凭证放入部署环境的密钥管理设施，不写入 Git；生产与测试账户隔离。对滥用检测、投诉处理、暂停账户和费用争议制定流程。运营后台也遵循最小权限，人工调账应有理由、证据与复核。

12 / OPERATIONS

可观测性、成本与恢复

一条追踪链，两个经营视角

将 request_id → attempt_id → 上游 request_id → usage 证据 → 凭证串联。追踪可采样，账务事实不可因采样丢失；避免把 request_id 作为高基数指标标签，详细定位放在日志 / 追踪中。

运行健康

平台拒绝与上游失败分开统计；记录首有效内容时延、总耗时、活跃流、队列等待、背压、熔断状态、数据库锁等待、结算积压与未知 usage 占比。

经营健康

收入、所有尝试的上游成本、未确认成本敞口、退款 / 拒付、支付费、促销消耗和基础设施费用分开。按租户、模型和渠道观察贡献毛利。

单次贡献 = 确认净收入 − 全部上游尝试成本 − 支付 / 退款成本 − 可归属基础设施成本
该式为运营分析口径，不替代财务收入确认。未知上游成本单列；重试成本与促销额度不可漏计。

售卖币种与采购币种不一致时，保存独立成本币种和固定的汇率快照；首版建议只开一种用户钱包币种。不要将充值额直接当成当期调用收入。

候选服务目标 压测后批准

  • 账务正确性：双扣、跨租户读取、无依据放开余额在验收中为零容忍。
  • 平台增量开销：定义“排除上游与主动排队的网关处理时间”，建议试点 P95 < 100 ms；必须在约定负载和环境下测量。
  • 用量完整度：正常完成且上游提供 usage 的请求，建议 99.9% 在 60 秒内完成结算；未知证据不混入成功样本。
  • 可用性：建议试点以月度 99.5% 为内部观察目标，同时报告端到端成功率与平台自身错误率；不是对外 SLA。

容量估算先看长连接

并发存活请求约等于到达率 × 平均存活时间。例如纯假设的 5 请求 / 秒、平均流长 20 秒，约有 100 条同时存活的流。压测还要覆盖长尾流长、慢客户端、突发、租户偏斜、供应商限额及数据库热钱包；不能只报告普通 HTTP QPS。

部署数量与扩容路线 尚未部署

阶段数量与职责可用性边界
开发验证1 台：C、Go / Worker、PostgreSQL 同机。适合验证，所有组件共用一个故障域，不具备 HA。
低成本试点2 台：一台 C + Go / Worker，一台数据库。应用与数据库仍各有单点；分开部署不等于高可用。
商业起步建议2 台业务 VM，跨可用区，每台 C + Go / Worker；另配高可用托管负载均衡及主备 PostgreSQL。“2 台”仅指业务机，托管服务及数据库主备资源另计。任意一台故障，另一台须能承受约定峰值；做 CPU / 内存资源隔离。
独立扩容阶段4 台起步：2 台 C 网关 + 2 台 Go / Worker，再按负载分别增加；数据层与入口资源另计。共享请求与账务状态，不依赖某台机器内存；Worker 可重复领取但最终结算必须幂等。

网关扩容看活跃 SSE 流、文件描述符、内存、出口带宽与事件循环延迟；Go 看预占与结算延迟、吞吐和任务积压。数据库先优化索引、短事务、连接池与热钱包锁竞争，再评估规格升级、报表读副本；余额判断与扣费不得依赖有延迟的读副本。新增服务器不会提高上游账户配额。扩缩容阈值、机器规格、区域、价格和容量基线需压测与预算审批后确定，不在此虚构报价。

高可用的验收条件

  • 负载均衡健康检查与自动摘除、多可用区故障隔离、N−1 容量均需测试。Redis 如成为必需共享限流依赖，须有 HA 或经验证的保守降级路径，不能成为新单点。
  • 发布先停止接收新请求，再等待连接排空并设置有界等待。节点宕机后，旧 SSE 流通常会中断，不能自动迁移续传；新请求可切至健康节点，不代表旧请求可安全重跑。
  • 数据库故障切换需检测、旧主隔离与单写者保障。核实托管方案的同步持久化和已确认账务 RPO；异步复制可能丢失最近事务，同步复制也有延迟与可用性取舍。[9]
  • 提交结果未知时先查询唯一凭证，再幂等重试本地事务；不得将数据库重试变成重新调用付费模型。缺失 usage、断流和不明结果进入差异单，不能直接当免费或立即解冻全部额度。
  • 模拟网关、Go、数据库主节点、可用区与网络故障，检查请求状态、扣费、证据恢复和告警。只有实际通过约定的故障与恢复验收，才能宣称达到目标，不能凭两台机器承诺 SLA。

备份、迁移和事故恢复

建议 PostgreSQL 采用可恢复的备份方案与连续 WAL 归档 / PITR，并验证完整恢复链。官方文档说明了基础备份结合 WAL 回放的恢复机制。[8] Redis 可重建；凭证加密密钥需有独立、受控的恢复路径。

  1. 历史候选灾难恢复目标：RPO ≤ 15 分钟、RTO ≤ 2 小时；仅适用于待评审的备份恢复场景，不是在线故障切换目标，也不等于可以接受丢失已确认账务。两类目标须分别审批并通过演练量测。
  2. 事故期间暂停新的计费请求，保留请求与上游证据；切换前确保单一有效写入者，避免双主扣费。
  3. 恢复数据库后，对账本做余额重建与分录平衡检查；重放 Outbox 依靠幂等，不触发新的上游生成。
  4. 核对备份截止之后上游仍可能产生的费用、支付回调与撤销操作；未收敛差异先挂账。
  5. 数据库迁移先扩展兼容结构再切换，保留回滚预案；月度恢复演练及高风险升级前演练作为建议。
13 / TECH CHOICES

技术选型：以团队能力与验证结果为准

当前讨论以 C + libevent 转发核心、Go 业务与账务、PostgreSQL 为分层示例；仍为提案，未批准开发或采购。用户进一步提出比较全 C、全 Go 与 C + Go，三种均待评估，尚未选择。逻辑职责不依赖语言绑定。

领域当前提案待验证与取舍
调用网关C + libevent，参考 OES 事件驱动与状态机思路。验证 SSE 解析、TLS、取消、背压、内存安全与工具链；不能因采用 C 就假定更快。
业务 / 账务Go 模块化业务服务及 Worker。明确并发、内部契约与错误处理；每次预占是关键路径，不只是管理后台。
全 C 对照C 网关 + C 业务 / 账务，仍保留相同逻辑边界与 PostgreSQL 事务。需要验证业务迭代、数据库与支付接口生态、内存安全和测试维护成本；不能以语言一致替代可靠账务设计。
全 Go 对照纯 Go 网关 + Go 业务，保留相同逻辑边界。用相同硬件、模拟上游和负载比较长连接、慢客户端、尾延迟、CPU / 内存与开发维护成本，再决定是否采用双语言。
主存储PostgreSQL 权威账本、预占与 Outbox。版本、主备持久化、切换及恢复能力待确定；内存和 Redis 不保存唯一余额。
缓存 / 异步Redis 按需；先数据库 Outbox + Worker。依据共享限流、积压和吞吐证据引入组件，避免新的单点；投递重复依靠幂等收敛。
前端 / 部署普通管理控制台，React / Vue 或服务端渲染待定；初期容器化，不强制 Kubernetes。两台业务机加托管 HA 数据层是部署建议，不是现有资源；选区、预算与长连接限制需确认。

多设备开发约定

GitHub 作为源代码与文档的同步点。每台设备开始前检查工作区并拉取，使用分支隔离较大任务；切换设备前提交并推送清晰的小步改动。不要同步生产数据库、真实密钥或本地凭证。依赖版本、数据库迁移、样例配置和本地启动步骤应入库；真实环境变量各设备独立配置。

后续建议建立 ADR（架构决策记录）：记录问题、备选、选择、后果、验证方式与日期。首批 ADR 应覆盖 API 子集、后端语言、账务模型、流中断收费、未知用量处理和上游授权。

14 / DELIVERY

分阶段路线与验收条件

按证据进入下一阶段，不在需求未定时承诺日历工期。每阶段结束需记录验收结果与未决事项。

P0 · 决策与验证

先把边界写清楚

完成首批客群访谈、上游授权核实、API 子集、币种及计费政策选择。

退出条件：可签字确认的决策表；至少一个合法可用上游；断线 / 未知用量政策明确；测试预算和负责人明确。

P1 · 单供应商技术闭环

先做可恢复的一次调用

在测试额度环境完成鉴权、普通 / SSE、usage、预占与结算、状态查询。

退出条件：断线、超时、并发和崩溃注入后不双扣；余额可重建；任何未决记录能被扫描发现。

P2 · 多供应商与试点

验证抽象是否成立

第二个供应商、能力矩阵、明确路由、限流熔断、用户账单与对账台。

退出条件：适配器契约测试通过；无透明危险重试；固定负载下达到批准的性能目标；恢复演练通过。

P3 · 正式收费准备

让资金和运营可闭环

支付商验证、充值 / 退款 / 拒付、权限、告警、客服与隐私流程。

退出条件：支付回调去重与金额核对通过；合规 / 合同核实完成；账单能对到采购成本；事故与争议有人处理。

P4 · 依据证据扩展：企业组织能力、更多协议与模型、多地区部署。图像 / 音频 / 视频在独立评审后进入；它们可能按张、时长、分辨率或任务计费，不能硬套文本 Token 账单。

开发时必须覆盖的验收矩阵

类别可执行验证通过标准
计费单元与性质测试大整数、边界 Token 数、价格版本、舍入、缓存子集、缺失字段。同一证据可重复计算；金额无漂移、无重复包含。
并发与幂等预算只够一次时并发发起多请求；同幂等键重复；结算重复投递。不会超额放行；一个逻辑请求最多一张初次消费凭证。
流协议UTF-8 字符跨分片、多行事件、usage 空值、流内错误、未知事件、慢客户端。内容和终止状态正确；有界内存；无遗漏的结算记录。
故障注入预占后崩溃、上游已接受时断网、usage 后崩溃、提交结果丢失、恢复重放。不盲目重发；每个请求最终收敛至结算 / 释放 / 有负责人差异单。
安全与隔离跨租户枚举、撤销 Key、日志扫描、恶意上游地址、大请求、权限提升。跨租户访问被拒；密钥不进入日志；地址与资源限制有效。
运维与真实对账备份恢复、真实小额上游样本对账、统计与账本重建、目标负载长连接压测。恢复目标实测达标；差异可解释；采购账单与内部证据可对应。

以上是后续业务开发的验收计划，不表示已执行。当前交付仅为此 HTML 文档及 README 入口。

开发前优先回答的 8 个问题

D01

首批服务谁，为何愿意付费？

决定首个使用场景与验收指标；建议先访谈开发团队。负责人：产品，时间：P0。

D02

哪些上游账户可用于此商业模式？

列供应商、合同依据、区域与配额；无授权证据不上生产。负责人：经营，时间：P0。

D03

首版协议和功能子集是什么？

建议先文本普通 / SSE；明确是否包含工具调用、缓存和推理维度。负责人：产品 + 后端，时间：P0。

D04

未知用量、流中断和取消怎样收费？

选择证据优先级、冻结期限、估计是否可入账、后补扣费与平台承担条件。负责人：产品 + 经营，时间：P0。

D05

币种、余额、价格与退款政策怎样定义？

确认记账精度、舍入、价格生效、预付模式与支付渠道。真实收费前完成；原型只用测试额度。

D06

选择什么技术栈和部署区域？

比较全 C、全 Go 与 C + Go 对照原型，依据团队熟悉度、供应商地域、预算、SSE 与故障测试确定。负责人：技术，时间：P0–P1。

D07

需要多大容量、保留什么数据？

确定并发、平均 / 长尾流长、日志与证据留存、客户数据限制、RPO / RTO。负责人：技术 + 产品，时间：P1 前。

D08

谁处理故障、差异与客户争议？

指定值守、调账复核、告警升级和上线签字角色；即使团队很小也需明确责任。时间：试点前。

下一步建议

先完成 D01–D04 和一个小型技术验证：一条真实授权的文本请求，在正常结束、断流、重复提交和进程重启四种情况下，都能得到可解释的调用与账务结果。再根据验证结果确认最终技术栈与开发计划。

16 / REFERENCES

术语与官方来源

核心术语

Token：模型处理的计量单位，不等同于字数。
SSE：HTTP 事件流格式，用于逐步传输结果。
Tenant：拥有独立权限、预算和数据边界的客户主体。
Attempt：逻辑请求中的一次实际上游尝试。
Reservation：预占 / 冻结额度，不是最终消费。

工程术语

Outbox：在业务事务内记录待处理事件，再由后台可靠投递。
Idempotency：重复处理同一业务动作不重复产生副作用。
PITR：恢复到指定时间点。
RPO / RTO：可接受数据损失窗口 / 恢复服务时长。
ADR：记录架构选择及理由的决策文档。

    支持 include_usage 与中断可能缺失最终 usage 的描述；只引用该端点，不扩大为所有 OpenAI API 的统一语义。

    支持 message_delta usage 累计值、流内错误与新事件类型的描述。

  4. [4] Google — Understand and count tokens

    支持事务隔离与序列化失败需要重试本地事务的说明；不提供跨供应商网络调用的原子性。

    支持限流计数、过期与竞态处理的说明。

    支持基础备份与 WAL 回放的恢复机制；RPO / RTO 需要实际演练，不能由机制本身保证。
