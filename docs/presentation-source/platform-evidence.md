## 本轮 08–13 章示例边界

- **多项目故事是规划示例。** 第 09 章三个品牌、项目名称与并行制作流程均为假设，不代表真实客户、部署或试点成果。平台展示的是项目 AI 支出；项目利润还需收入、人力和其他成本，不能由 AI 账单独立推出。
- **调用追踪与项目归属分开。** 普通 API 可记录每次调用，平台可管理自身任务与尝试；这些技术标识本身不证明属于同一业务项目。只有已有任务/批次携带可靠的项目关联，或客户明确配置关联规则，才归集项目费用。API Key 是凭据，不天然等于项目；共用 Key、相似提示词或自动聚类均不能作为确定账务归属的依据。缺少可靠信息时单列待归属，不要求所有客户额外填写业务编号。
- **账单展示结构，不展示收益。** 第 11 章未填金额、单价、试点数量或节省比例。调用与重试等费用类别必须互斥，同一次实际消费不因出现在多个视图而重复计入。金额未定保留待核，归属不明另列待归属；用量缺失不补零，待核费用不冒充已确认金额。传输、存储与平台服务按实际规则核算，基础追踪拟不单列收费不等于这些资源免费。
- **缓存用于同品牌的文本任务。** 第 12 章共用输入行指同一请求优化前后保留完整品牌规范、固定资料和当次文案需求；不同任务的 A / B / C 需求仍可不同。左列待测基线纳入客户已有缓存与流程优化，不预设原调用零命中。右列环形图表示供应商在实际命中时复用已有前缀计算，本次需求与输出仍需计算；它不是命中率、计算量份额或节省比例图，也不是答案复用或视频生成本身的缓存。收益取决于实际命中及供应商规则，同模型、完整输入和同验收要求下仍需验证质量、时延与完整成本。
- **响应中断不等于生成失败。** 第 13 章按供应商可提供的查询、回调或对账证据核对执行与用量，不保证每个端点均能查询或取回结果。示例仅在确认生成成功、结果仍可获取且授权有效时交付已有结果，因此本例无新增生成调用；原调用费用证据继续保留，费用有据才确认。执行状态、结果可用性与账务状态分别维护，恢复结果无需把尚未取得的费用证据补成已确认。无法确认时保留待核并按约定处理，不盲目再次生成，不承诺全链路恰好一次或所有异常均能恢复。

## 最新架构解释与必须保持的关系

以下为内部研发依据；投资人页面用业务职责表达，不逐项展示实施方案。

- **初期单活 Kernel。** 根据研发对话最新修正，先保留集中调度核心，不预设它是吞吐瓶颈，也不预先为吞吐拆分。页面现在只写“Kernel · 业务中枢”，不再展示“初期单活”。可靠状态、备节点接替与容量验证是独立工作；历史容量反馈不能沿用为 TokenHarbor 性能指标。
- **主链是逻辑职责。** 页面为客户 → 接入与负载均衡 → Portal → Kernel → Dispatcher → 供应商；原项目规划将接入代理具体写为 Nginx。Portal 负责客户连接和 SSE 输出；Kernel 管规则、预算及状态；Dispatcher 管供应商协议。图中的双向箭头不规定所有流内容必须逐跳穿过 Kernel，SSE 回程仍待原型确认，相关实现图已从投资人版移除。接入代理不决定余额或扣费。
- **连接限制与任务并发分开。** 旧 Portal 在本节点内维护用户/IP 的已鉴权 HTTP 连接数，Kernel 传播配置；它不是全局在途任务、模型 RPM/TPM 或供应商并发的完整控制。定位：`oes_source/httpportal/tcplink.c` 的连接增减与 `check_ipauth()`、`dataload.c` 的 `http_limit` 计算。TokenHarbor 的传输槽、执行任务槽和费用预算需要分别设计。
- **资源交付与账务分开。** 图片/视频结果可经供应商链接或平台托管交付；Kernel 关联任务与资源状态，不代表文件字节必须经 Kernel。授权、有效期、转存与留存按接入方案确定。生成成功但下载失败时，保留生成及费用证据，优先重传仍可获取的既有结果。
- **恢复不等于再生成。** 生成、资源交付、账务、通知分别记录状态。供应商回调由适配职责处理，平台给客户的签名通知由投递职责处理；客户端断线、通知失败和下载失败都不能直接推导供应商未执行。执行未知先查询核对，通知重试不新建模型尝试。
- **结算以可靠证据与事务为准。** 初次结算凭证唯一；迟到或更正证据用独立调整凭证关联原记录。调用前预占、attempt 登记、用量证据和最终账务需有持久确认，不能用旧内存余额加异步增量 SQL 宣称全链路恰好一次，也不能按 SSE chunk 反复舍入扣费。

第 11–13 章三项亮点连续呈现。第 14 章所述“门槛”是需要建设和验证的积累方向：复制同类服务需要持续覆盖供应商变化、建立场景评测并验证异常恢复；这不是对竞争者当前能力的调查结论，也不意味着供应商或其他平台无法做到。

## 少输入、优化与三组成本对照

基础管理拟由平台自动生成 `request_id`、必要的异步 `task_id` 和实际供应商 `attempt_id`，不要求额外业务任务编号。本轮页面以普通 API 的调用记录、可靠任务/批次关联和待归属记录说明渐进形成项目视图的体验，具体实现名留在维护依据。技术关联不等于理解客户真实业务意图；平台生成的标识也不自动带有业务项目含义。同一提示词再次生成可以是新的合法请求。可选 SDK 在首次发送前生成幂等键并在重试时复用，不能把相同内容自动当成重复消费。基础追踪“拟不单列收费”是产品方向，不表示模型、存储、检索、评测等资源没有费用。

前缀缓存保留完整输入，收益按实际命中和供应商计价规则计算；每次请求仍独立生成。摘要、上下文选择、模型替换、延后批处理会改变内容或交付，按约定启用并评测，不承诺质量无损或必然省钱。

| 对照组 | 必须纳入的内容 |
| --- | --- |
| A 当前直连 | 客户已有缓存、重试与流程策略，以及全部调用和其他处理费用 |
| B TokenHarbor | 平台策略效果，全部模型尝试、额外处理与平台费用 |
| C 同等优化直连 | 客户直接采用同类缓存和流程优化后的效果与完整费用 |

三组使用同一任务集、相同底层价格、约定质量和时延。费用项不重复计算；失败、重试、摘要、检索、评测、回退等成本计入相应项。**单位成功任务成本 = 完整费用 ÷ 验收通过任务数**，仅在有业务验收反馈时计算；缺少反馈时报告技术交付指标。平台相对 C 组的增量还应观察接入、维护和排障工作，不能预设成本优势。这些均为试点验证设计，尚非已完成实验。
